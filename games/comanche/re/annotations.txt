# Durable annotations for the 32-bit flat Comanche image.
#
# This file, not a Cutter project or a rizin .rzdb, is the system of record.
# A binary project database cannot be diffed, reviewed, or merged, and this
# repository's convention is that generated listings stay ignored while durable
# conclusions are committed as text. Analyse in Cutter; write what you proved
# back here; regenerate the tool state from here.
#
# Addresses are flat game addresses: image offset 0x1700 into the LOAD MODULE
# (after the 512-byte MZ header). tools/re/carve-flat.py produces a raw binary
# that loads at base 0x0 with exactly these addresses.
#
# Columns, whitespace separated:
#
#   kind  address  extent  name  # evidence
#
#   kind    func   an entry point with proven callers or control flow
#           table  an array whose element size and count are established
#           data   a classified object that is not an array
#           string text with a known terminator convention
#           pad    filler or alignment with no owner
#   address 8 hex digits, flat
#   extent  size in bytes, or - when the end is not yet established
#   name    unique identifier, [A-Za-z_][A-Za-z0-9_]*
#
# Prefix the kind with ? for a candidate. A ? entry is exported to rizin as a
# comment only: it never defines a function or a data type, so an unproven guess
# cannot quietly become the thing later work is built on. Promote it by removing
# the ? and replacing the evidence with what established it.
#
# Every row needs evidence. "It looks like a table" is not evidence; the bytes,
# the reader, or the observed behaviour is.

# --- the seven-way dispatch-slot / variant system ----------------------------
# Correction to the original 0002C69D/0002C6D5 rows: `jmp dword ptr [0x2c69d]` is
# opcode ff25 9dc60200 - a MODRM of mod=00,rm=101, disp32 only, no index register.
# That is a plain, non-indexed jump through ONE fixed pointer, not an 8-entry
# table read. The "8 in-content dwords" the original evidence quoted were real,
# but they were read as a raw memory dump rather than derived from the
# instruction's own addressing form, and the form does not index anything.
#
# The actual mechanism, read from 0002BA36-0002BA93: a mode/key byte selects
# 1-5, and for that index the code copies one dword from each of seven 6-entry
# "variant" tables into seven fixed "slot" dwords - dispatch_table_a and
# dispatch_table_b (now dispatch_slot_2c69d/_2c6d5) are two of the seven slots,
# which is why they read as statically populated AND are overwritten at runtime:
# both are true, at different times. jmp/call through the slot then reaches
# whichever variant was last selected. Every slot currently holds variant [0],
# the bare-ret default at 0002B9F6, in the unmodified file.
data   0002C649  4     dispatch_slot_2c649      # call dword ptr [0x2c649] at 0002BA9A  elem=4

# --- terrain span renderer --------------------------------------------------
# The original draws vertical spans through fully unrolled code, and this is the
# heart of it. 0x6BF0 is not a pointer table: the callers do
# `lea ebx,[ebx*4+0x6bf0]` then `jmp ebx`, which jumps TO the computed address,
# so the table holds 4-byte code stubs. Entering N stubs in and falling through
# writes 256-N pixels - Duff's device. `inc ch` advances ecx by 0x100 per pixel,
# so the destination is a 256-byte-stride buffer addressed as ch:cl = row:column.
#
# This is the DOS counterpart of src/render.s:draw_span, and it is the strongest
# available evidence that the port's vertical-span structure matches the
# original rather than only matching the VoxelSpace reference.
func   00006BF0  3FF   span_writer_unrolled     # 255 copies of `mov [ecx],al / inc ch`, then `mov [ecx],al / ret` at 00006FEC
func   0000AF50  23FD  column_span_emitters     # bank 1 of 3: 192 blocks, each with a distinct mov cl,imm8 column, its own esp slot (24-127) and return address, ending lea ebx,[ebx*4+0x6bf0] / jmp ebx
func   0000F320  1474  column_span_emitters_96  # bank 2 of 3: 96 blocks, same skeleton, strides 48/57/64; start corrected from 0000F323 - block 0's `mov cl,0x3f` is at 0000F320, and 000138A3 jumps to it
func   0001C1A0  778   column_span_emitters_40  # bank 3 of 3: 40 blocks, same skeleton, uniform 48-byte stride

# The three banks are 192, 96 and 40 columns and were found by scanning for the
# 7-byte `lea ebx,[ebx*4+0x6bf0]` signature: 328 occurrences image-wide, in three
# clusters. Only bank 1 is reachable by recursive descent; the other two are
# entered through pointers the patcher below installs.
#
# The blocks are self-modifying. Each contains `mov al, byte ptr [ebx+0xffff]`
# whose 0xffff displacement is a PLACEHOLDER, patched at init with the real
# source address. Any static read of that field is meaningless, and a port must
# reproduce the effect - a per-column source pointer - not the mechanism.

# --- VGA mode setup, vsync and page flip -------------------------------------
# 00015855-00015DD0 divides cleanly into seven routines: each one's terminating
# ret lands exactly on the next entry, so the extents are bounded rather than
# guessed. Two of them are res_open_a and res_open_b, which have been on record
# without extents since the loader family was first identified and now have them.
#
# 00015B78 is the most-called routine found anywhere in this image - 43 call
# sites - and it does three things, not one:
#
#   mov dx,0x3DA / mov ecx,-1 / in al,dx / test al,8 / loopne   ; vertical retrace
#   inc [00019DE0] / cmp [00019DE0],0xA / jb ...                ; 10-frame window
#     mov eax,[00019DDC] / mov [00019DE4],eax                   ; publish the count
#     zero [00019DDC] and [00019DE0]                            ; and restart it
#   mov dx,0x3D4 / mov eax,[00019CAC]                           ; CRTC display start
#
# So it is the frame boundary: wait for retrace, update a 10-frame rate counter,
# then set the CRTC start address from [00019CAC] - the page flip. That single
# routine is what AGENTS.md's "publish the display buffer at VBL" replaces, and
# the 43 call sites are how thoroughly the original leans on it.
#
# 00015C14 sets the display mode: `mov ax,0x12 / int 0x22` through the extender,
# then programs the Attribute, Sequencer, Graphics and CRTC registers directly
# (0x3C0, 0x3C4, 0x3CE, 0x3D4) - a tweaked mode rather than a plain BIOS one,
# which is why the port cannot infer the geometry from a mode number.

# --- the game object table --------------------------------------------------
# handler_table_20040 was correctly read as "two halves of 130, displacements
# base-4, indices 1-based" - but it is not a standalone handler table. It is
# fields 0 and 1 of a structure-of-arrays for 130 objects, and the same 1-based
# stride continues for ten more dword fields and then fourteen byte fields.
#
# Twelve dword fields, array k at 00020040 + k*0x208, code displacement k-4.
# All twelve displacements appear as `[reg*4 + disp]` in reached code, which is
# what establishes the series; every field is uniformly initialised, i.e. one
# repeated default value per field, exactly as a linker emits:
#
#   0 @00020040  130 x 0002514D   per-object draw fn, called only from the
#                                 draw stage's 00024BFC `mov eax,[ecx*4 +
#                                 0002003C] / call eax`. The other 20 sites
#                                 that name this displacement are spawn-time
#                                 writes, which is why no plain call reaches it
#   1 @00020248  130 x 00024860   per-object tick fn (default)
#   2 @00020450  zero             per-object model pointer, filled at runtime
#   3 @00020658  zero             second model pointer - see object_draw_rotated;
#                                 0002514D walks field 2 and 00024E05/00024FED
#                                 walk field 3 with the identical "3D" check
#   4 @00020860  zero             sideways offset from the viewer, per frame
#   5 @00020A68  zero             forward distance from the viewer, per frame;
#                                 the sort key, the cull in 00024C45, and the
#                                 scale input for 0002519D
#   6 @00020C70  130 x 40000000   X position
#   7 @00020E78  130 x D4800000   Y position
#   8 @00021080  130 x 40000000   previous X
#   9 @00021288  130 x D4800000   previous Y
#  10 @00021490  zero            11 @00021698 zero
#
# The 6/7 -> 8/9 pairing is not inferred from the identical defaults alone.
# 00024860, field 1's own default, is the routine that performs the copy:
# `mov eax,[ecx*4+20C6C] / mov [ecx*4+2107C],eax / mov eax,[ecx*4+20E74] /
# mov [ecx*4+21284],eax`, with ecx the object index - so fields 8 and 9 are the
# previous-tick copies of 6 and 7, saved per object per tick.
#
# 0002514D, field 0's default, walks field 2 as a pointer: `mov edi,[ecx*4 +
# 0002044C] / add edi,[edi+4] / add edi,0x302 / cmp word [edi],0x4433`. 0x4433
# is the bytes 33 44, ASCII "3D" - a model-record magic, which is what makes
# field 2 a per-object 3D model pointer rather than an unknown dword.
# The series extends two fields EARLIER than first recorded. 0001FE34 and
# 0001FC2C also appear as `[reg*4 + disp]` in reached code, giving fields -1 and
# -2, so the table begins at 0001FC30 - exactly where band_bitpattern_table ends
# - and the 1,040-byte all-zero stretch noted there is those two fields
# (2 x 520). 14 dword fields, 0001FC30 + 14*0x208 = 000218A0, which is precisely
# where the byte fields start: the whole structure is contiguous.
#
# Field -1 (disp 0001FE34) is speed. 00023A8C establishes it, and the field
# semantics below, in one routine: it restores X/Y from the previous-tick copies,
# then `movzx ebx,byte [ecx+0002189F]` (heading), `mov eax,[ecx*4+0001FE34]`
# (speed), `imul [ebx*8+00032320]` -> subtract from Y, `imul [ebx*8+00032120]`
# -> add to X. So byte field 0 is a heading index into a sin/cos pair at
# 00032320/00032120 with stride 8, and field -1 is the scalar it scales.
# The object table is a structure of arrays, so every field is already a
# contiguous array of one width - which is why it can be annotated field by
# field and converted for a 68k, where a record of mixed-width fields could
# not be. The two aggregate rows that used to stand here, object_table_dwords
# and object_table_bytes, said 14 x 130 dwords and 13 x 130 bytes but gave no
# way to emit either.

# --- shared sine table -------------------------------------------------------
# One table serves both the object physics and the terrain renderer, which is
# why 00032120 turned up in the renderer setup earlier without an explanation.
# 512 entries of 4 bytes over a full revolution, amplitude 0x7FFFFFFF (Q31):
# entry 0 is 0, entry 128 is 0x7FFFFFFF exactly, and the curve is sin to within
# rounding across the range. COSINE IS THE SAME TABLE AT +0x200, i.e. +128
# entries = +90 degrees - there is no second table.
#
# That resolves two earlier readings. 00023A8C indexes it as [ebx*8 + 00032120]
# and [ebx*8 + 00032320] with an 8-bit heading, so headings use 256 of the 512
# steps. terrain_setup_192/96 index it as `lea ebp,[ebp*4+00032120]` and read
# [ebp] and [ebp+0x200], so the pair they store into [00019CB0]/[00019CB4] is
# the sin and cos of the view heading, not an unexplained "scale pair".
# The table is 640 entries, not 512. Entries 512-639 are a byte-exact copy of
# entries 0-127: a quarter-wave overhang so that the cosine read, which is
# index+128, never runs past the end. The largest cosine index, 511+128 = 639,
# lands at 00032B1C - the last dword in the image, which ends at 00032B20. The
# table is sized exactly to the image end, so a port must either keep the
# overhang or mask the index.
table  00032120  A00   sine_table_q31           # 640 x 4-byte Q31 entries: 0-511 one revolution ([0]=0, [128]=0x7FFFFFFF, [384]=-0x80000000), 512-639 repeat 0-127 as the cosine overhang. cos = same table + 0x200. Read [ebx*8+...] by object physics (8-bit heading) and [reg*4+...] by the terrain setups  elem=1

# 00026211 is the detail-level screen, and it CONFIRMS the .DTL load address.
# That address was derived earlier purely from size-matching - the unclassified
# span at 00019EE0 was 5,004 bytes and each .DTL is 5,004 bytes. Here the code

#
# 0002B89D is the palette install and it completes color_component_ramp. It
# copies 256 triples from 0002A380 into palette_rgb, and it does NOT treat the
# three components alike: R and G go through `mov al,[eax + 0002B7D0]` - the
# ramp - while B is only `shl al,1`. An earlier note here said every component
# went through the ramp, and that is wrong.
#
# What matters more is where the result goes. palette_rgb has exactly one
# reader, the matcher at 0002B854, so this builds the space colours are MATCHED
# in and nothing else. The display palette never passes through the ramp: both
# DAC uploads send raw components, 0002A9E7 from 00015F84 and 0002AA00 from

# --- by-kind sweep of the remaining holes ------------------------------------
# Working the tail region-by-region had reached diminishing returns, so this
# pass partitions everything still unclassified by signature instead. Three
# kinds came out of it, and two traps.
#
# TRAP 1: ASCII is not text. The longest "string" left in the image, 882 bytes
# at 00001018, is the pair table "000102...FF" - `%02X` for 0..255, verified
# byte-exact against a generated expectation. The 121-byte run at 0002D202 is
# the repeated-word data in the data segment. Neither is a string, and a bulk
# "record every long ASCII run as a string" pass would have mislabelled both.
#

# `high.dtl`, `openmus.ms3`, `p2.dta` scored as table-shaped on a word-density
# heuristic; they are resource filenames.

# Input: PC scancode -> ASCII, in scope for the first milestone.
# 000280C1 does `movzx ebx,bl / mov al,[ebx + 000019E9]`, tests the result for

# --- where the perspective actually lives ----------------------------------
# The renderer's inner loop has no arithmetic because build_projection_tables
# did it first, at 00015AD9, into the 0xFA00 block:
#
#   page i, entry k:  row = clamp((k - 128) * slope_i + bias_i, 0, 255)
#   slope_i = high32(dtl2[i] * [00019CEC])      dtl2 = 0001A6B4
#   bias_i  = dtl3[i]                           dtl3 = 0001AA9C
#
# One page per DEPTH STEP, not per column, and the marcher walks them: the
# depth loop ends with `inc word ptr [00019EDD]` at 0000F2DE, which is
# frame_view_word plus one, so it adds 0x100 and selects the next page. An
# earlier note here said page 0 was the only reachable one and called that a
# contradiction to chase. It was a grep that searched for 00019EDC and never
# saw the instruction that names 00019EDD.
#
# So dtl_column_count is a depth-step count, not a column count. The five .DTL
# tables divide up as:
#
#   dtl0 00019EE4  sideways step per column at depth i, into esi/ebp
#   dtl1 0001A2CC  forward distance of depth step i, moves the sample line
#   dtl2 0001A6B4  the 1/z term the slope is built from

#   dtl4 0001AE84  not identified

# the 1/z, and dtl3 climbs 15405 -> 35062 and stays there. 35062 >> 8 is 136,

# camera height to rows as low as 60.

# --- bitmap font block -------------------------------------------------------
# A complete, self-describing proportional font, and unlike the music data this
# one is in scope: the first milestone includes the HUD and menus.
#
#   +0x000  "KF4b" signature, then height 0x0A (10 rows) and a 1 byte at +5
#   +0x008  128-byte width table, indexed by character code; 104 nonzero, 2..10
#   +0x088  128-word offset table, offsets relative to the BLOCK BASE 00027276
#   +0x188  glyph data, width*4 bytes per glyph
#
# The glyph stride is not assumed. Across every consecutive pair of used
# characters the offset delta equals width*4 exactly - 2->8, 3->12, 4->16, 5->20,
# 6->24, 7->28, 8->32, 9->36, 10->40 - so a glyph is 4 bytes per COLUMN, one
# 32-bit column mask, of which the header's 10 rows are used. The renderer
# confirms the column-major reading: `mov edx,[esi]` loads one column and
# `shr edx,1` walks it downward a pixel at a time.
#
# Two consumers, both decoded:
#   000268DB  string width: lodsb over a NUL- or 0xFF-terminated string,
#             `movzx edx,byte [eax+0002727E]`, summing widths into edi
#   00027196  glyph blit: width lookup, `movzx esi,word [esi*2+000272FE]`,
#             `add esi,00027276` to absolutise, then `mov al,2 / mov dx,0x3C4 /
#             out dx,ax` (VGA Sequencer map mask) and the unrolled column walk,
#             advancing the destination by 0x52 between pixel pairs
#
# The first glyph offset is 392, and 00027276 + 392 = 000273FE, exactly the end
# of the offset table - an internal consistency check that the base-relative
# reading is right.
data   00027276  8     font_header              # "KF4b" signature; [+4]=0x0A glyph height in rows, [+5]=1. Nothing reads these bytes: text_render_loop uses 00027276 only as the base its word offsets are added to, `add esi, 00027276` at 000271B0, and the smallest offset among the 104 characters with a width is 392, which lands on font_glyph_data at 000273FE. The fields are byte-wide, and the glyph height at +4 is confirmed by the renderer independently of the header: the blit walks ten rows, `add edi, 52` ten times, taking two bits per row from a dword column mask, 20 `shr edx,1`  elem=1
table  0002727E  80    font_width_table         # 128 bytes, character code -> advance width (0 = absent, else 2..10)  elem=1
table  000272FE  100   font_offset_table        # 128 words, character code -> glyph offset relative to 00027276  elem=2
data   000273FE  994   font_glyph_data          # width*4 bytes per glyph, column-major, 4-byte column masks, 10 rows used; ends 00027D92  elem=1

# that is 30^2, 55^2 and 15^2, and 30+55+15 = 100. The weights are a perceptual

# --- terrain renderer: three detail levels, complete ------------------------
# What the flat 0000F318 gap actually holds, and it is the core of the game.
# Three renderers share one skeleton, each bound to one of the three span
# emitter banks already on record. Reading them settles what those banks are:
#
#   detail  setup            renderer         fill via   marcher (records)  bank
#   high    00007D25 (12842) 0000D950 (6600)  [19C98]    0000D9FB (96)      1: 192 blocks
#   mid     000107A0 (12362) 000137F0 (8293)  [19CA0]    0001389F (48)      2:  96 blocks
#   low     inlined          ~0001B2xx        [19C9C]    0001B345 (20)      3:  40 blocks
#
# The skeleton, read from 0000D950 and 000137F0 which are instruction-for-
# instruction identical apart from their setup target and fill pointer:
#
#   call <setup>                      ; per-column ray tables, scales
#   mov ax,0x38 / mov gs,ax           ; GS = extended-memory arena (GDT row above)
#   mov eax,[<fill ptr>] / call eax   ; clear the viewport through viewport_fill_*
#   sub esp,0xC0 / mov ecx,0x30 / rep stosd   ; zero a per-column horizon array
#   mov edi,[00019CD4] / mov ebx,[00019CD8]   ; viewer X, Y
#   per column: imul ray tables [0001A2CC] and [00019EE4] by the scales at
#     [00019CB0]/[00019CB4] to get the ray origin and per-step delta
#   per step:  shld ebx,edx,0xa / shld ebx,edi,0xa   ; 10-bit X:Y map pack
#              add al,gs:[ebx]        ; sample the heightmap in the arena
#              mov ah,[eax]           ; through a lookup
#              cmp ah,[esp+N]         ; against this column's running horizon
#              ja  <emitter block>    ; draw the span, then continue the march
#
# That is a voxel-space column marcher: for each column, step outward, sample
# the map, and emit a span whenever the sample rises above the highest already
# drawn for that column. The `cmp ah,[esp+N]` / `ja` records ARE the marcher -
# the same shape recorded as depth_band_dispatch, which is simply the low-detail
# renderer's copy of it. Each marcher's `ja` targets stride 48 bytes through its
# own bank, starting at that bank's block 0 (0000AF50, 0000F320, 0001C1A0),
# which is what binds each renderer to one bank.
func   00007D25  322A  terrain_setup_192        # per-column ray/scale setup for the 192-block bank; opens mov eax,[19D04] / movzx ebx,byte [19D86] / add eax,[ebx*4+19D94]; called only from 0000D950

# --- how the terrain renderer actually works -------------------------------
# Recovered by reading 0000D950 (prologue), 0000D9FB (the unrolled march) and
# 0000AF50 (an emitter block) together. The three detail levels are the same
# machine at 192, 96 and 40 columns.
#
# Column state. The prologue does `sub esp,0xc0` and zeroes 0x30 dwords - 192
# bytes, one per column, the highest screen row drawn in that column so far.
# That single allocation is what fixes the viewport at 192 columns; the
# emitter bank's 192 blocks and the marcher's stack displacements 0x18..0x77
# both index into it.
#
# Loop order is depth outside, column inside, which is what makes the occlusion
# byte work. The outer loop at 0000D99A advances the sample line one depth step
# using [ecx*4+0001A2CC] times the view sine and cosine at [00019CB0]/[00019CB4],
# and takes each column's ray from dtl_column_tables at [ecx*4+00019EE4]. Each
# unrolled record then steps sideways along that line with `sub edx,esi` and
# `sub edi,ebp` and samples one column.
#
# Sampling. The map index is rebuilt from scratch every record - `xor ebx,ebx`,
# `shld ebx,edx,0xa`, `shld ebx,edi,0xa` - taking the top ten bits of each
# 10.22 coordinate, so a 1024x1024 map wraps for free. The height comes from
# `gs:[ebx]`, gs being selector 0x38 loaded at 0000D959, and the colour from
# `[ebx + disp32]` in the emitter.
#
# That displacement reads as 0000FFFF in the image, and it was written up here
# as the two maps sitting a 64K span apart less a byte. They do not. It is a
# placeholder: 00005BC5 onwards stores colour_map_base into 0000AF54,
# 0000AF84, 0000AFB4 and on at a 48-byte stride - the disp32 field of every
# emitter block's source load - which is the patch run span_emitter_patch was
# already on record for. Both maps are 1 MB allocations from
# heap_alloc_aligned and their spacing is whatever the allocator gave them.
#
# THE PROJECTION IS A TABLE, NOT A DIVIDE. This is the part that does not look
# like the textbook renderer. The inner loop is:
#
#     mov eax, dword ptr [esp]      the current depth's row table
#     add al, byte ptr gs:[ebx]     offset it by the height sample
#     mov ah, byte ptr [eax]        and read the screen row out
#
# Only AL is added, so the index wraps inside 256 bytes: the value read is
# table[(base_low + height) & 0xFF]. There is no arithmetic per sample at all,
# one add and one load, which is the whole reason the inner loop is this short.
#
# What the table IS remains open, and the obvious guess is wrong. It would be
# natural to call it a per-depth perspective table with the camera altitude in
# its low base byte, but the pointer is frame_view_word at 00019EDC, whose low
# byte comes from `mov al,[00019DFC] / not al / shr al,1` at 0000D98C - and
# 00019DFC is the heading accumulator, not the altitude. Nor is the pointer
# reloaded per depth: it is pushed unchanged from the same variable on every
# iteration of the depth loop, so one table serves all depths.
#
# 00019E5C is identified and so is its filler, both recorded in full beside
# projection_tables. In short: heap_alloc_aligned gives it 0xFA00 bytes on a
# 0x100 boundary at 00005B99; build_projection_tables at 00015AD9 fills it with
# one 256-byte page per depth step, each page mapping a height byte to a screen
# row by `row = clamp((k - 128) * slope_i + bias_i, 0, 255)`; and the depth loop
# selects the page with `inc word ptr [00019EDD]` at 0000F2DE. The slope and
# bias come from .DTL tables 2 and 3, so the projection is asset data, which is
# why nothing in the image looked like a projection constant. Until that is settled the projection constant this port
# stands in for - PROJ_SCALE - has not been recovered, whatever else here has.
#
# Emitting. `cmp ah, [esp+slot]` against the column's stored top, and `ja` to
# that column's emitter block. The block stores the new top, computes
# `old - new` as a byte, and enters span_writer_unrolled at
# `[ebx*4 + 00006BF0]`. The subtraction underflows on purpose: the writer is
# 255 copies of `mov [ecx],al / inc ch` at 4 bytes each ending in a `ret`, so
# entering 4*(old-new) in draws 256-(old-new) pixels, which is new-old. The
# run length is the byte wrap.
#
# The staging address is ecx = (ch << 8) | cl. `mov cl,imm8` in each block is
# that block's column and `inc ch` steps one row down, so the buffer is 256
# bytes to the row. The emitter returns by pushing the address of the next
# marcher record and jumping - 0000AF50 pushes 0000DA05, which is the
# instruction after the record that called it.
#
# Not recovered: where the per-depth row tables are built and what scale they
# encode, which is the projection constant this port still stands in for; and
# whether the 96 unrolled records cover half of the 192 columns in two passes
# or the bank is indexed another way.
