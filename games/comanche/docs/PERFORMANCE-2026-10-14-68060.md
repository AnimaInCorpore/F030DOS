# The 68060 image: TT-RAM and an exact faster frame (2026-10-14)

Goal: make the accelerator image (`TARGET_CPU=68060`) playable. The game route
itself already ran on it - menus, briefing, live flight, weapons, crash and
debrief were driven through Hatari's control FIFO with real IKBD key events -
so the work was frame time. Every change below keeps the rendered output; none
is a behaviour or detail switch, and the 68030 image runs the same source.

## Measurements

Emulator evidence, not real-Falcon or real-CT60 timing. Hatari 2.6.1-devel
built from `../F030Arcade/third_party/hatari` (commit 639fadf6, binary of
2026-09-22). The 060 profile is the F030Arcade one: `--cpulevel 6 --cpuclock 32
--fpu internal --ttram 64 --addr24 false --cpu-exact true --compatible true`,
EmuTOS 1.2.1 (`etos512de.img`), 14 MB ST-RAM, RGB 60 Hz. The 68030 rows are the
cycle-exact 16 MHz core with TOS 4.02. Frame rate is replay records per VBL
between instruction-bound `frame_driver` breakpoints at `demo_cursor = 13 + 8K`
(the method of `PERFORMANCE-2026-09-30.md`); cycles are the profile's total.

Live flight in mission 1 ("Werewolves on Patrol", cockpit, no lock), counted
from `flight_iteration` against VBL over ~500-VBL windows: 15-17.7 fps before,
20.9-21.7 fps after. Game logic runs one DOS tick per rendered frame, as the
original does, so this is also the game's pace.

Hatari's 060 model charges about one cycle per instruction and nothing for
cache misses or superscalar pairing, so its figures track instruction count.
Two things it gets wrong in opposite directions: `MULU.W` costs 11 cycles
there against 2 in the MC68060 manual (so `cpu_muls64` is overstated), and
ST-RAM writes on a real CT60 go over the 16 MHz bus shared with Videl (so
`render_row_shear`'s 153,600-byte copy to the scanout page is likely
understated). A hardware measurement is still owed.

## What changed

1. **TT-RAM load (060 image only).** PRG flags 7 instead of 1
   (`tools/build-run.sh`). BSS is 8.3 MB - both maps, terrain_history, the
   sprite banks - and on an accelerated Falcon ST-RAM is the slow memory.
   Everything a device reads is already `Mxalloc(...,0)`: both scanout pages
   (`start.s`) and the sound DMA ring (`sound.s`). Without TT-RAM, TOS ignores
   the bits. This alone took the cockpit from 7.9 to 13.6 fps.
2. **Marcher sample** (`TERRAIN_SAMPLE`, 8 -> 5 instructions). The Y cell
   selects its height-map row from `ring_maprow` (1024 relocated row
   addresses, in DATA), the X cell indexes it, and the colour is read at the
   fixed distance `MAP_COLOUR_DELTA` from the same byte. The bias add of
   0000D9F6 is folded into the page pointer: `ring_page2_table` stores every
   projection page twice, so `page2[bias + h]` is `page[(bias + h) & 255]`.
3. **Target-view march** (`mfd_march_target_view`): the same row read, the
   loop counter in a register, and the per-ring archive taken from a
   256-entry table (`mfd_archive_row`) and stored three times.
4. **Map MFD** (`mfd_draw_map`): the same row read instead of ten shift and
   mask instructions per pixel.
5. **Sky fill**: `sky_rgb_build` expands `sky_image` through `sky_palette`
   once per family load, column-major and doubled to the pixel pair, so a row
   is one `move.l (a1)+,(a0)`.
6. **Depth sort** (`object_depth_sort`): 00024B81's pick - deepest key, lowest
   position on a tie, exchanged with position d7 - is found from eight-slot
   block maxima instead of a full rescan per pass. Same picks, same exchanges.
   Checked against the original scan on 20,000 random 130-slot arrays with
   heavy ties, and byte-equal `object_order` at both benchmark records.
7. **Wide products on 060** (`cpu_mulu64`/`cpu_muls64`): four 16x16 products
   with one carry fold, the signed form inlined. All 4,772 products of
   `tools/check-cpu-compatibility.py` pass on both CPUs; the dump hash is the
   recorded `937041ae...`.

## A bug found on the way: the target silhouette archive

`mfd_march_target_view` filled its per-ring archive (`mfd_target_silhouette`,
read by the 00024B17 target pass to clip the target sprite) at rings R, R+2
and R+4 instead of R..R+2: an extra record step after every row. Rings 3k+1
were a step stale and ring 250 was written past the table. It also added the
offset with `ADDA.W`, which sign-extends: from ring 205 (205 x 160 > 32767) the
rows went 64 KB back, into `terrain_history` rows 189-201 - the persistent
console page - about 6.7 KB a frame whenever a target was locked at HIGH
detail. Fixed by the consecutive stride and `ADDA.L`.

Against the DOS frame of DEMO1 record 20 (`build/frame-pair/dos-r20`, page x
4, 2:1 sampled), within a 24-unit RGB tolerance, the target view matches 3,491
of 3,520 panel pixels after the fix against 3,453 before, and 714 of 720 in the
tank's box against 676 - the tank's bottom rows are now clipped by the terrain
as in the original. DOS writes the target silhouette only for the ring each
step starts on (its other rings keep the main view's archive); the port's
three-record fill remains a recorded adaptation, not a DOS equivalence.

## Verification

Each step was A/B-compared at both benchmark records against the build before
it, by dumping `terrain_history`, `ring_silhouette`, `mfd_target_silhouette`,
`object_order`, `flight_palette`, `mfd_view_occl` and both scanout pages:

- External records 60..80: every buffer and both pages byte-identical at every
  step except the archive fix (archive only).
- Cockpit records 10..20: all buffers identical; 60-130 pixels differ in the
  effect over the designated tank (x 136-155, y 112-124) and its copy in the
  target view. That effect's frames are drawn from the PRNG that the Timer C
  hook advances (`flight_shake_tick`), so its phase follows frame duration -
  the same spot differs between two DOS captures (see "The first
  complete-frame pair" in `PORTING-PLAN.md`). The 68030 capture at record 20
  differs from master in exactly that box (61 pixels).

`tools/check-attract-timing.py` reaches attract flight with no target
exception on both CPUs, but its screen-countdown assertion is stale on master
too: `attract_blit_x` now sits between `attract_active` and `attract_screen`,
so the ten bytes it samples are no longer the fields it expects. Not fixed here.

Harness fixes made to get these runs at all, worth knowing elsewhere:

- The F030Arcade Hatari rejects `symbols <file>` at the TEXT breakpoint
  ("program TEXT address invalid"); `symbols autoload exec` works.
- GEMDOS resolves `--auto C:\comanche_d.tos` to the stripped `COMANCHE.TOS`
  (long name, 8.3 filesystem), so no symbols load. Stage the symbol build
  under an 8.3 name.
- A breakpoint whose command file ends in `quit` needs `:trace`; without it
  Hatari drops to its interactive prompt and the run times out.
