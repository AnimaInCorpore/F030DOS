# Project: Star Wars TIE Fighter (1995) — Decode, Disassemble + Prove, Understand, Port

**Goal:** fully analyze the DOS game *Star Wars: TIE Fighter (Collectors CD-ROM,
1995)* — code and data — and port its observable behaviour to the Atari
Falcon030. Byte-exact reconstruction is evidence for a recovered encoding, not
the definition of port fidelity.

## Mandatory function-level port policy

The hashed shipped DOS executable and its captured execution are the sole
behavioural authority. Reassembly, decompiler output, a recovered source tree,
the browser reference, and 68000 code are evidence or implementations; none
may overrule DOS. For every function represented in browser or target code,
maintain the `METHOD.md` §4.2 function record: DOS identity and evidence,
recovered contract and fixtures, browser/target symbols, and an explicit
difference ledger against DOS. Record and prove even “no difference”; an
unresolved difference is `Unproven` and cannot enter a supported path. Start
the deterministic browser reference with the first function; use its controlled
experiments to identify function roles, contracts, side effects and Falcon
seams, then confirm each finding against DOS before recording it. Land its
fixtures before or with each supported target slice.
## Implementation-source links

Every JavaScript/browser and 68000/m68k function source that implements or exposes a recovered DOS function must carry an adjacent comment or docstring linking to the durable function record and naming the disassembled DOS function symbol plus canonical range/entry (for example, `DOS: FUN_0000_1234; record: <stable-function-record>`). Use the same stable function ID in both implementation sources; a separate map or file-level comment is not enough. Code with no DOS counterpart must say `N/A - platform replacement` or `Target artefact` at the definition.

## Boot chain (verified)

```
run.bat          menu: picks sound (SB16 / MT-32 / SC-55) via CONFIG -set, copies IMUSE.INI, runs TIE.EXE
  └─ TIE.EXE     plain 16-bit Watcom launcher (31 KB, entry 0x110C; the "DOS4G
                 hybrid / 32-bit image @ 0x39EC" reading is withdrawn 2026-08-21 —
                 `analysis/32bit/P1.5-launchers.md`)
       ├─ "Loading TIE-Fighter CD.  Please wait...."; probes \astream\a.wrk
       ├─ detvesa (DETVESA.EXE VESA detection; SciTech UNIVBE prompt block if none)
       └─ exec z_tie2__.exe (args incl. /trebla marker)
            └─ Z_TIE2__.EXE  12 KB Watcom 16-bit guard (genuine MZ): without /trebla →
               "You must run TIE.EXE for TIE-Fighter CD"; else execs dos4gw.exe +
               z_tie__.exe (args /trebla /320; env DOS4GPATH/PATH)
                 └─ Z_TIE__.EXE  THE GAME (see layout below)
                      └─ its own CD check → "ERROR #3: You must insert TIE-Fighter CD"
```

**Chain verified end to end on `img/tie.hdd` (2026-08-20)**: DOS boots, `C:` is
recognised, TIE.EXE reads `c:\tie.cd`, Z_TIE2__ clears its `/trebla` guard, DOS4GW
loads the 32-bit image — and only then does the game's *own* CD detection fail.
`ERROR #3` / `You must insert` appear **only in `Z_TIE__.EXE`** (tree-wide grep),
at img+`0x0A983E`/`0x0A98BF`. It is not the MSCDEX `INT 2F/AX=1500h` check (that
immediate does not occur in the image) and not `CDROM.CFG` (deleting it, as the
disc's `SUPPORT\INSTALL.BAT` does, changes nothing). See `analysis/qemu-boot.md`.

Other executables: `BOOTTIE.EXE` (LucasArts boot-disk maker, Borland C++), `TIEAUTO.EXE`
(auto-launch helper), `INSTALL.EXE`/`INSTLOW.EXE`/`Z_INST__.EXE` (installer),
`IMUSE.EXE` (Interactive Music Environment runtime; `IMUSE.INI` is an IMUSE device table:
FM4.MDR, SB16.WDR, ROLAND.MDR, GUSMIDI.MDR …), `DOS4GW.EXE`, `UVCONFIG.EXE`.
`/trebla` = anti-double-launch marker token passed TIE.EXE → Z_TIE2__ → Z_TIE__
(same check inside game image: "You must run TIE.EXE for the game.\n" @ img+0x0A981A);
`/320` = resolution arg (320×200).
Config: `CDROM.CFG` = `0 8202`, `FOPTION.CFG` = `2`, `INSTALL.CFG` = `2`.
`TIE.CD` = 8 bytes `C:\TIECD`, read by TIE.EXE from the literal path **`c:\tie.cd`**;
on the CD it lives at the **root**, not inside `TIECD\` (so: `game/SWTieCD/TIE.CD`).
Without it TIE.EXE runs the CD installer instead of the game — verified 2026-08-20.

## `Z_TIE__.EXE` — the game (1,031,495 B, MZ stub + standard Watcom LE)

**Master doc: `analysis/ztie.md`** (uwexe-style: identity, layout, address
mapping, open questions, artifacts). Re-resolved 2026-08-21
(`work/audit_headers.py` / `audit_fixups.py` — the "DOS4G OLX hybrid /
private header" model is withdrawn, old readings quoted in
`analysis/DOS4G-header.md`). Essentials:

- **MZ stub** (10.7 KB Watcom 16-bit, entry file 0x36E) + real `e_lfanew` =
  0x2A50 → **standard LE module**: obj1 (code) base 0x10000, file
  `0x3D800..0xE8800`; obj2 (data) base 0xC0000, file `0xE8800..0xFBD47`
  (+ 0x32470 B BSS). Entry obj1+0x7B4E4 → linear **0x8B4E4**, file 0xB8CE4
  (Watcom C/C++32 CRT). Data pages end exactly at EOF.
- **Fixups are the xref index**: 27,438 records, 100 % 32-bit-offset/internal;
  `python work/audit_fixups.py --target=OBJ:OFF` lists every source site
  (raw operands in the file are unrelocated — immediate scans cannot work).
  The old "11-byte thunk records / vector table / entry-stub pair" were all
  fixup-record and header structures misread.
- Functions: `analysis/32bit/functable_v2.txt` (4,030 fns, 84.6%; addresses
  valid as file offsets — runtime column superseded); string pools
  img+`0x0A9800..0x0AB600` (startup/CD/IMUSE: `/trebla`, `You must run TIE.EXE…`),
  img+`0x0B9000..0x0BE000` (scene .WRK paths), `.TFR`/`__temp__.tfr` @ 0x0BACE4
  (`img+X` = file 0x3F000+X, a pure file-offset alias).

## QEMU headless boot & diagnostics (verified lessons)

**Decision (user): no sound in the first implementation.** Run without any sound card —
QEMU: pass no sound device (the build doesn't support `-soundhw` anyway); 86Box: start
the machine without SB16/MT-32. Note: `run.bat` has **no "no-sound" option** (only
SB16 / MT-32 / SC-55 via `CONFIG -set` + IMUSE.INI copy) — for a silent first run, exec
`TIE.EXE` directly, or pick option 1 (SB16, `mididevice=default`) with no card present
and see whether the game/IMUSE degrades gracefully. Fallback if the game refuses to start
without a sound driver: attach an SB16 (86Box or DOSBox Staging, since this QEMU build
has no audio).

Full byte-level detail + probe sources: `analysis/qemu-boot.md`. Key gotchas that cost
hours, verified against QEMU 11.1.0 (Windows) + MSYS2 gdb 17.2:

- **This QEMU build is stripped**: no `-soundhw sb16` ("invalid option"), and the
  **serial sink is a no-op** — `-serial file:` and modern `-chardev file,id=… -serial
  chardev:…` both leave the file at **0 bytes** even after ~1000 executed `out 0x3F8`
  (confirmed via GDB: EIP parks at the `jmp $` right after the OUT). **Headless
  observation = write files to the image** (`ECHO … > A:\LOG.TXT` in AUTOEXEC.BAT),
  then read offline with `mtype`; or inspect memory via GDB.
- **Working images** (in `img/`): **`tie.hdd`** = 256 MB, MBR + FAT16 partition at
  LBA 63, genuine DOS 6.22 boot record — **boots to `C:` with `C:\TIECD` populated**
  (`work/build_dos_hdd.py`); `bootprep.img` = genuine DOS 6.22 Disk1 (bootable floppy).
  **Floppy `A:` boots** under SeaBIOS *and* the two genuine 486 BIOSes
  (`-bios roms/phoenix_winpro486e_103.bin`, `-bios roms/award_sis486g_fullyes.bin`);
  AUTOEXEC batches run and write files.
- **~~`C:` (IDE) is NOT recognized by DOS~~ RESOLVED 2026-08-20.** The old reading
  ("rejection is DOS-side; suspect CHS truncation or `AH=48`") was wrong. Real cause:
  `tie-dos.img` was a **superfloppy** — FAT at LBA 0 with *no MBR partition table* —
  and DOS assigns drive letters to partitions enumerated from that table, so a
  partitionless fixed disk gets no letter. Its BPB was also broken (`rootent=0`,
  `total32` > the drive's CHS size). Fixed by building a real partitioned disk; the
  five invariants are asserted at build time in `work/dosimg.py`. See
  `analysis/qemu-boot.md`.
- **Headless runs end themselves**: `C:\QUIT.COM` writes to QEMU's isa-debug-exit
  port (0xF4) → exit code 21. This supersedes the `probe*.com` / `sendkey` work.
- **mformat's boot sector is QEMU-incompatible** (hangs at `rep movsw`, `0x7c4f`, CX=256
  never decrements). Use a genuine DOS 6.22 boot sector instead.
- **mtools gotchas**: `mtype`/`mcat` on a **missing** file dump the raw image (looks like
  content but is the image) — verify existence with `mdir` first. `mcopy -o` to overwrite.
  `mformat -F -i img` (no drive letter) works despite broken MTOOLSRC.
- **GDB without a target executable mis-decodes** 16-bit real-mode code as x86-64. Trust
  raw byte dumps + explicit register reads, not GDB's disassembly.
- **Parked machine state** = EIP `0xFF53` (SeaBIOS region) with a blank text screen =
  boot-failed/halted.
- **GDB timing**: always pass `-s` (opens :1234). `-S` halts at reset (needs `continue`).
  Boot/failure happens in seconds; a late attach is fine *if the machine has parked*, but
  attaching with `-s` while the machine is mid-boot can perturb the boot (one run parked
  mid-boot and the batch never ran).
- **QMP `sendkey`** (`-qmp tcp:127.0.0.1:4444,server=on,wait=off`,
  `human-monitor-command sendkey <k>`) works but is **timing-sensitive** — interactive
  FDISK keying is unreliable (keys get eaten by the `A:\` prompt).
- **Hand-assembled 16-bit COM** (raw bytes, no header; all regs zero at entry) is a good
  probe vehicle for INT 13 / INT 21 file I/O. Watch inline-opcode correctness (one attempt
  had a bad `FBC1` = #UD).
- **Resolved:** DOS rejected `C:` because the old image was a superfloppy with
  no partition table. The current MBR + FAT16 `tie.hdd` boots and exposes `C:`;
  see `analysis/qemu-boot.md`. Do not revive the superseded probe task.
