# Project: Ultima Underworld (1992, Sierra) — Decode, Disassemble + Prove, Understand, Port

**Goal:** fully analyze the DOS game *Ultima Underworld: Stygian Abyss (1992)* —
code and data — and port its observable behaviour to the Atari Falcon030.
Byte-exact reconstruction is a proof technique for recovered encodings, not the
port's definition of fidelity.

## Mandatory function-level port policy

The hashed shipped DOS executable and its captured execution are the sole
behavioural authority. Reassembly, decompiler output, a recovered source tree,
the browser reference, and 68000 code are evidence or implementations; none
may overrule DOS. For every function represented in browser or target code,
maintain the `METHOD.md` §4.2 function record: DOS identity and evidence,
recovered contract and fixtures, browser/target symbols, and an explicit
difference ledger against DOS. Record and prove even “no difference”; an
unresolved difference is `Unproven` and cannot enter a supported path. Start
the deterministic browser reference with the first function; use its controlled
experiments to identify function roles, contracts, side effects and Falcon
seams, then confirm each finding against DOS before recording it. Land its
fixtures before or with each supported target slice.
## Implementation-source links

Every JavaScript/browser and 68000/m68k function source that implements or exposes a recovered DOS function must carry an adjacent comment or docstring linking to the durable function record and naming the disassembled DOS function symbol plus canonical range/entry (for example, `DOS: FUN_0000_1234; record: <stable-function-record>`). Use the same stable function ID in both implementation sources; a separate map or file-level comment is not enough. Code with no DOS counterpart must say `N/A - platform replacement` or `Target artefact` at the definition.

## `UW.EXE` (561,744 B, 16-bit Borland Turbo C++ 1990)

- MZ (standard layout, verified): `e_cblp = 0x130`, `e_cp = 822`, `e_crlc = 0xC68`
  (3,176 entries, all valid), `e_cparhdr = 0x320`, `e_ss = 0x638B`, `e_sp = 0x80`,
  `e_ip = 0x0000`, `e_cs = 0x0EC5`, `e_lfarlc = 0x3E` (reloc table @ file 0x3E),
  `e_ovno = 0`. No `e_lfanew`/extended header exists — bytes at file 0x3C straddle
  the header/relocation-table boundary and misread as 0x10000 if parsed as a 4th
  field; there is no `NE`/`NP` anywhere.
- CRT string @ file `0x5F2F4`: `Turbo C++ - Copyright 1990 Borland Intl.` → **16-bit TC++ 1990**.
- Disassemble as **16-bit x86** (`e asm.bits=16`), load base `0x10000` → entry file
  `0x11E50` (header `0x3200` + (`e_cs=0x0EC5`<<4) + `e_ip=0`); file `0x10FC5` (an old
  claimed entry address) is confirmed data, not code.
- **Load model (measured on boot, 2026-08-20 — `analysis/uwexe.md` §13):** the DOS
  loader maps only the 822-page image (file 0x3200..0x66B2F) at **linear 0x5960**,
  i.e. **load segment 0x0596, PSP 0x0586, `runtime linear = file + 0x2760`**;
  DGROUP/`DS` = **0x61A5** = file 0x5F2F0 (proven by the Borland CRT banner at
  `DS:0x0004`).
- The 141,088 B tail (file 0x66B30..0x89250) is **not** self-loaded code: it is a
  Borland **`FBOV` overlay pool**, **64 overlay units** reached through **602
  `INT 3Fh` thunks**, swapped into a buffer above the stack. Ghidra maps it as
  block `CODE_TAIL` where **address = file offset** (verified) — but a *runtime*
  address in the overlay buffer must not be translated with the image delta; it
  will "resolve" to a `CODE_TAIL` function name anyway, because 559 functions
  tile the region. See `analysis/ghidra.md`, `analysis/uwexe.md` §13.3.
- **The overlay map is resolved** (2026-08-23, `analysis/uwexe.md` §13.6): the
  159-row segment table at file 0x5D860 (the `FBOV` `exeinfo`) covers *every*
  linker segment; the 64 rows with `type == 3` are the overlaid ones, each a
  32-byte stub header (pool offset, code size, fixup size, entry count,
  runtime resident segment) plus its 5-byte thunks. `work/overlay_map.py`
  prints the unit table and checks it against a live run.
- **Ghidra address ↔ file offset: `ghidra_linear = file + 0xCE00`.** The obvious
  `0x10000 + file` is wrong by 0x3200 (the header is not mapped) and yields
  well-formed wrong names. See `analysis/uwexe.md` §8.
  Phase 1 artifacts: 2,685-fn sweep → `work/uw16.txt`, strings →
  `work/uw_strings.txt`.
- Embedded file references (verified strings): `DATA\uw.cfg`, `DATA\weapons.dat`,
  `DATA\skills.dat`, `DATA\chrgen.dat`, `DATA\cmb.dat`, `DATA\cnv.ark`, `DATA\lev.ark`,
  `DATA\strings.pak`, `DATA\grave.dat`, `ZDATA\objects.dat`, `comobj.dat`,
  `DATA\terrain.dat`, `DATA\light.dat`, `DATA\mono.dat`, `DATA\shades.dat`,
  `DATA\xfer.dat`, `crit\assoc.anm`, `data/pals.dat`, `data/allpals.dat`, `player.dat`,
  `babglobs.dat`/`bglobals.dat`, `font5x6i.sys`, `font5x6p.sys`, `font4x5p.sys`,
  `fontbig.sys`, `fontchar.sys`, `.voc`, `uw00.xmi`, `sounds.dat`, `SAVE0\lev.ark`,
  and `uwedit.exe` (level-editor reference).

## Data inventory & format findings (headers verified)

### `DATA/` (73 files)
- **`.GR`** sprite graphics (ARMOR_F/M, BODIES, DOORS, OBJECTS, WEAPONS, SPELLS, …):
  e.g. `ARMOR_F.GR` `01 40 00 07 01 00 00 b8 06 00 00 69 0c 00 00 …` — header +
  u24-LE offset table to sprite blobs. `BODIES.GR` `01 0a 00 2f 00 00 00 e8 09 00 …`
  (same shape, different header). Format TBD.
- **`.TR`** (F16/F32/W16/W64 — texture/terrain resources by tile size?):
  `F32.TR` `02 20 34 00` then u32-LE offset table @ 0x50 (`d8 00 00 00, d8 04 00 00, …`
  0x400 stride); `W64.TR` `02 40 d2 00` (table 0x1000 stride). Count/stride fields TBD.
- **`.BYT`** fixed 64,000 B level/screen buffers (BLNKMAP, CHARGEN, CONV, MAIN, OPSCR,
  PRES1/2, WIN1/2). `BLNKMAP.BYT` filled `03`, `WIN1.BYT` zeroed.
- **`.DAT`** game data (PALS.DAT = palette `00 00 01 00 00 00 3f 25 3f …`, WEAPONS.DAT,
  TERRAIN.DAT, MONO.DAT, LIGHT.DAT, OBJECTS.DAT, PLAYER.DAT = **save file**:
  301 B, starts ASCII `GROKEY\0` = player name).
- **`.SYS`** fonts (FONT4X5P 497 B, FONT5X6I 1028 B, FONT5X6P 901 B, FONTBIG 3949 B,
  FONTCHAR 2679 B, FONTBUTN 1234 B).
- `WEAPONS.CM` (32 B), `3DWIN.GR` (258 B).
- **`LEV.ARK`** (290,864 B, level archive): `87 00 1e 02 00 00 26 7e 00 00 2e fa 00 00 36 76 …` —
  header/entry table TBD (u24 pairs? u32s? values unsorted).
- **`CNV.ARK`** (558,007 B, conversation/conversion archive): starts with **ascending
  u32-LE offsets** (`40 01 00 00, 02 05 00 00, 48 19 00 00, 9a 4b 00 00 …` = 0x140, 0x502,
  0x1948, 0x4b9a) → offset-prefixed container.
- **`STRINGS.PAK`** (227,230 B, global string table): `b5 00 09 8f ff ff 0a a3 ff ff …`
  — pointer/hash table TBD (decode like TIE's STRINGS.DAT once format is known).

### `CRIT/` (65 files) + `CUTS/` (72 files) — page-based graphics
- `CRxxPAGE.N00/.N01` (critic pages) and `CSxxx.N00…N05` (cutscenes), e.g.
  `CR00PAGE.N00` (17,461 B): `00 20 00 01 02 03 ff 04 ff 05 ff ff ff ff 06 ff …`
  (RLE-like encoding? TBD).
- `CRIT/ASSOC.ANM` (384 B): 8-byte ASCII table of creature names
  (`gngob32`, `skela`, `lizman`, `bat`, `wiza`, `spider`, `gazer`, `troll`, …) then
  binary — creature↔animation association table.

### `SOUND/` (66 files)
- 42× **`.VOC`** = standard **Creative Voice** files (`43 72 65 61 74 69 76 65 20 56 6f 69 63 65`
  "Creative Voice File", block `0x0a` type 0x1129 …) — decode with ffmpeg.
- 24× **`.XMI`** = **IFF `FORM`/`XDIR`** container (`46 4f 52 4d … 58 44 49 52 49 4e 46 …
  43 41 54 …`) — custom XMI music format, TBD.
